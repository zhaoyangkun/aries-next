# MySQL 到 PostgreSQL 数据映射

> 最后验证日期：2026-09-07（对照 `migrations/` 全部 9 个 Migration 与旧版仓库 `aries/models/` 逐表核对；ETL 已经过一次真实数据演练）

**回答什么问题**：旧版 Aries（MySQL）的每张表、每个字段迁移到 Aries Next（PostgreSQL）的哪张表、哪个字段，经过什么清洗与转换。
**写给谁**：编写和评审 Migration Code 的开发者。只有表映射、清洗规则、Validation Query 和 Rollback 行为明确后，才能实现对应的数据写入。

旧版表结构以旧版仓库 `aries/models/` 下的 GORM Model 为准（`gorm.Model` 隐含 `id` / `created_at` / `updated_at` / `deleted_at`）；目标表结构以 `migrations/` 下的 SQLx Migration 为唯一权威来源，本文只做映射说明，不复制完整 DDL。

## 全局转换规则

| MySQL | PostgreSQL | 转换规则 |
| --- | --- | --- |
| Unsigned Integer ID | `bigint GENERATED BY DEFAULT AS IDENTITY` | 保留原 ID，迁移后重置 Sequence |
| `datetime` | `timestamptz` | 按旧站配置的 Timezone 解释，再转换为 UTC |
| `tinyint(1)` / `bool` | `boolean` | Preflight 阶段拒绝 0 和 1 以外的值 |
| `varchar` / `text` | `text` 或 `citext` | 在可行范围内按 UTF-8 原样保留；需要大小写不敏感唯一的标识用 `citext` |
| Soft Delete Timestamp | `deleted_at timestamptz` | 保留 `NULL` 和原删除时间 |
| JSON String | `jsonb` | 先验证 JSON，再转换为结构化数据 |

## 目标 Schema 与迁移机制

- 目标 Schema 由 `DATABASE_SCHEMA` 配置，只接受简单 Identifier；Backend 启动时自动执行 `CREATE SCHEMA IF NOT EXISTS`（见 `backend/infra/src/lib.rs`）。
- SQLx Migration 和业务 Query 使用同一个 `search_path`；Migration Validation 必须明确 Schema，避免错误读取 `public` 中的同名表。
- 所有结构变更只通过 `migrations/` 下的版本化 Migration，禁止运行时建表。

## Authentication 数据

`202608020001` 在目标库中扩展 `users` 并新增运行时表，这些表不从 Legacy MySQL 迁移 Session 或 Token：

| Target Table / Column | 数据来源 | 迁移规则 |
| --- | --- | --- |
| `users.role` | 人工复核 | `CHECK (role IN ('owner', 'editor', 'moderator'))`；首个管理员设为 `owner`，其他账号在迁移演练中显式映射 Role |
| `users.status` | 人工复核 | `CHECK (status IN ('active', 'disabled'))`，默认 `active` |
| `users.last_login_at` / `users.password_updated_at` | 运行时生成 | 不迁移 |
| `admin_sessions` | 运行时生成 | 不迁移 Legacy Session；切换后要求重新登录 |
| `password_reset_tokens` | 运行时生成 | 不迁移 Legacy Reset Token |
| `audit_logs` | 运行时生成 | Legacy Log 仅在后续确认审计价值后单独导入 |

`admin_sessions.token_hash` 与 `password_reset_tokens.token_hash` 只保存 Token 的 SHA-256 Hash（`bytea`），两表主键为 `uuid`。Session、Reset Token 和 Audit Log 的时间字段统一使用 `timestamptz`。

## Article 状态

Legacy Article 使用 `is_published` 和 `is_recycled` 表达状态，目标统一为 `status`（`CHECK (status IN ('draft', 'published', 'recycled'))`）：

| `is_published` | `is_recycled` | Target Status |
| --- | --- | --- |
| 0 | 0 | `draft` |
| 1 | 0 | `published` |
| 0 或 1 | 1 | `recycled` |

`published` Article 必须具有 `published_at`（`202608040001` 的 CHECK 同时要求 `title` / `slug` / `markdown_source` / `rendered_html` 非空白）。旧结构没有发布时间时，使用 `created_at` 作为替代，并在 Migration Report 中记录替代数量。

## Article 内容与版本

`202608040001` 使用以下 Target 字段和运行时表承载内容发布：

| Target Field / Table | 数据来源 | 规则 |
| --- | --- | --- |
| `articles.markdown_source` | Legacy `content` | 保留原始 Markdown；发布前必须非空 |
| `articles.rendered_html` | Legacy `md_content` 或重新 Render | 使用 `comrak` Render，并通过 `ammonia` Allowlist Sanitization |
| `articles.version` | 运行时生成 | 初始为 `1`（`CHECK (version > 0)`），每次内容更新或状态迁移递增，用于 Optimistic Lock |
| `article_revisions` | 运行时生成 | 不导入编辑过程；每次更新和状态迁移前保存 Source 与 Metadata Snapshot；`UNIQUE (article_id, revision_no)` |

`article_revisions.metadata_snapshot`（`jsonb`）保存 Title、Slug、Summary、Category、Tag、SEO 与发布设置，用于后续 Revision Restore。Password 只以 Hash 形式进入 Snapshot，不得写入 Report 或 API Response。

## 媒体库与站点设置

`202608050001` 在目标库中新增以下结构：

| Target Table | 数据来源 | 迁移规则 |
| --- | --- | --- |
| `media_assets` | Legacy `pictures` 与旧 `galleries` 行（每行一张图） | 默认尝试下载原图（15s 超时、20MB 上限、2 次重试）：成功按 server local storage 约定 `yyyy/mm/<uuid v7>.<ext>` 落盘并计算 `sha256`，`provider = 'local'`；失败或 `--skip-media-download` 时保留 `provider = 'legacy_url'` 的外链记录（`object_key = legacy/pictures/{id}` 或 `legacy/galleries/{id}`，URL 原样保留，`size` 由旧库 KB 换算 bytes）并逐条记入 Report；图库媒体行 ID 从 `max(pictures.id) + 1` 起顺序分配 |
| `media_usages` | 运行时重建 | 不迁移；由内容保存时的引用解析重建；`target_type` 限定 `article_cover` / `article_content` / `gallery_item`，`UNIQUE (asset_id, target_type, target_id)` |
| `background_jobs` | 运行时生成 | 不迁移；`status` 为 `pending` / `running` / `done` / `failed`；`kind` 见下方说明 |
| `site_settings` | Legacy `sys_settings` / `sys_setting_items` | 单行表（`id smallint` 恒为 1，Migration 预插默认值行）；迁移时选取 Site Name、Description、URL、ICP 备案号等映射字段，未识别的 Key 不迁移 |

`media_assets` 使用软删除（`status = 'deleted'` + `deleted_at`），物理删除只在零引用时由后台任务执行。`site_settings` 由 Migration 插入一行默认值，API 只允许更新不允许增删。

`background_jobs.kind` 当前允许 4 种：`media_cleanup`（物理清除软删除资产）、`import_markdown`（Markdown 批量导入预览）、`metadata_probe`（补探测图片尺寸）、`comment_notification`（评论通知，由 `202609050001` 扩展 CHECK 加入）。

## 评论与通知数据

`202609050001` 新增 `comments` 与 `email_deliveries`，`202609050002` 放宽了 Email 约束：

| Target Table / Column | 数据来源 | 迁移规则 |
| --- | --- | --- |
| `comments` | Legacy `comments` | 见下方字段级说明 |
| `email_deliveries` | 运行时生成 | 不迁移；评论通知邮件发送记录，`status` 跟踪 `pending` / `sent` / `failed` / `bounced` |
| `site_settings.comment_policy` | Legacy 评论策略映射 | `moderated`（默认）/ `closed` / `auto_approve`；旧站无评论功能时映射为 `closed` |
| `site_settings.comments_per_page` | 运行时配置 | 默认 20，`CHECK (comments_per_page BETWEEN 5 AND 100)` |

### `comments` → `comments`

| Legacy 字段 | Target 字段 | 规则 |
| --- | --- | --- |
| `type` + `article_id` / `page_id` | `target_type` + `target_id` | `type = 1`（文章）→ `target_type = 'article'`、`target_id = article_id`；`type = 3`（关于页）/ `4`（自定义页）→ `target_type = 'page'`、`target_id = page_id`；`type = 2`（友链页）旧版无对应 Link ID，统一映射 `target_type = 'link'`、`target_id = 0`，数据完整入库；新站前台暂无友链页评论展示（`resolve_target` 返回 None），属后续功能 |
| `root_comment_id` / `parent_comment_id` | `root_id` / `parent_id` | 重建层级；根评论 `root_id` 指向自身、`parent_id = NULL`；旧版 `0` 转换为 `NULL` |
| `nick_name` / `email` / `url` | `author_name` / `author_email` / `author_url` | 长度约束：`author_name` 1–60，`author_email` 0–254，`author_url` ≤ 2048 |
| `content` / `md_content` | `content_markdown` / `content_html` | `content` 是 Markdown 源文（1–2000 字符）；`content_html` 由 `comrak` 重新 Render 并 Sanitization |
| `is_checked` | `status` | `true` → `approved`；`false` → `pending`；`is_recycled = true` → `recycled`。旧版**没有** Spam 标记字段，`rejected` / `spam` 无迁移来源 |
| `device` | `user_agent_digest` | 原始 UA 经 Hash 后写入，不保存原文 |
| — | `ip_hash` | 旧版不存 IP，目标默认空串；新系统只存 Hash，不存原始 IP |
| `admin_user_id` | `is_admin_reply` | 非 `0` → `true`；管理员回复无访客 Email，`202609050002` 已将 `author_email` 约束放宽为允许空串 |
| `user_img` | — | 目标评论无头像字段，不迁移 |

评论状态机：`pending → approved/rejected/spam → recycled → approved`。`status` 的 CHECK 为 `pending` / `approved` / `rejected` / `spam` / `recycled`。

### `journals` → `journals`

| Legacy 字段 | Target 字段 | 规则 |
| --- | --- | --- |

### `galleries` / `gallery_items`

旧版 `galleries` 表**每行是一张图片**（`url` / `name` / `desc` / `location` / `category_id`），不是相册；目标的 `galleries` 是相册实体，`gallery_items` 才是图片条目。映射因此拆成两步：

| Target Table | 数据来源 | 迁移规则 |
| --- | --- | --- |
| `galleries` | 由 `categories` 中 `kind = 'gallery'` 的行聚合生成 | `category_id` 必填，`ON DELETE RESTRICT`；`slug` 唯一约束为部分唯一索引 `galleries_slug_key`（软删除行不占位）；`cover_media_id` 引用 `media_assets`，`ON DELETE SET NULL`；`status` 限定 `draft` / `published`；相册的标题、描述等 Metadata 无旧版来源，需迁移时生成或人工整理 |
| `gallery_items` | Legacy `galleries` 行 + `pictures` | 旧行 `url` 必须先落成 `media_assets` 记录（`media_asset_id` 为 `ON DELETE RESTRICT`）；`location`、`desc` 等字段映射到 `location` / `alt`；`UNIQUE (gallery_id, media_asset_id)`，迁移时去重 |

### `links` → `links`

| Legacy 字段 | Target 字段 | 规则 |
| --- | --- | --- |
| `category_id` | `category_id` | 可空，指向 `categories` 中 `kind = 'link'` 的行；FK 为 `ON DELETE SET NULL`（友链为软删除，`RESTRICT` 会让回收站中的友链永远阻塞分类物理删除，引用检查由应用层在删除分类前完成）；旧版 `0` 转换为 `NULL` |
| `name` / `url` / `icon` / `desc` | `title` / `url` / `icon_url` / `description` | `title` 1–100，`url` 1–2048，`icon_url` ≤ 2048；URL 仅允许 http/https（应用层校验） |
| — | `status` | 旧版无状态字段，默认映射 `active`；目标限定 `active` / `inactive`，软删除走 `deleted_at` |

### `navs` → `navigation_items`

| Legacy 字段 | Target 字段 | 规则 |
| --- | --- | --- |
| `name` | `label` | 1–60 字符 |
| `url` | `target_type = 'url'` + `url` | 旧版导航只有外部 URL，全部映射为 `url` 类型；内部目标（`article` / `page` / `category`）无迁移来源。互斥由 CHECK 保证：`url` 类型必须有 `url`，其余类型必须有 `target_id` |
| `open_type` | `open_in_new_tab` | `1` → `true` |
| `order_id` | `sort_order` | 原样保留 |

## 数据完整性与 Archive 机制

任何源数据只有三种去向：**迁入目标表**、**进入 Archive 文件**、**Report 计数**，禁止静默丢弃任何行或字段。

- Archive 为机器可读 JSONL（`--archive` 指定，默认 `migration-archive-<run_id>.jsonl`），每行 `{"table", "id", "fields": {...}, "reason"}`；整行未迁入的行带 `whole_row: true` 标记（Validate 对账据此区分行级与字段级归档）。
- Archive 与 Report 均不得包含密码 Hash、Secret 设置值与原始 UA（评论 `device` 只以 SHA-256 摘要入库）。
- 无目标字段的列（`users.signature`、`categories.count`、`tags.count`、`comments.user_img`、`navs.icon`）、旧渲染 HTML（`md_content` / `md_html`）、`themes` / `theme_settings` 全表、未识别的 `sys_setting_items` Key → Archive。
- 超出目标长度约束的数据（评论 > 2000 字符等）：Preflight 全量列出；`migrate` 默认遇违例即失败退出，显式传 `--truncate-violations` 才截断（原文进 Archive、记 Report repaired）。
- Zero Date 与越界时间：Extract 以字符串读取时间列（避免 sqlx 解码崩溃），Transform 显式转换；Preflight 将此类行列为硬错误，未经人工处理不进入 Load。

## 必须执行的 Preflight

- Username、Email、Category Slug、Article `url`、Page `url` 的重复与大小写冲突（目标为 `citext`）。
- User、Category、Tag、Comment、Page、Gallery 和 Association Row 的孤儿记录。
- Zero Date、非法时间和超出 PostgreSQL 支持范围的 Timestamp。
- Boolean Column 中不是 0 或 1 的值。
- Article 非法状态组合，以及没有稳定 URL 的 Published Article。
- 重复的 `tag_article` Association。
- 需要 Sanitization 的 Rendered HTML。
- JSON Setting 的格式错误与类型不一致。
- Legacy `comments.type` 不在 1–4 范围的值（硬错误）；`type = 2`（友链页）评论清单（统一映射为 `target_type = 'link'`、`target_id = 0`）。
- Legacy `galleries` 行引用的图片 URL 能否落盘为 `media_assets`。

## Migration Validation

每次 Full Rehearsal 至少输出：

- Source 和 Target Table Row Count
- Primary Key 最小值、最大值和缺失范围
- Article Markdown 与 HTML Content Hash
- Foreign Key 和 Association Count
- Invalid Row、Skipped Row 和 Repaired Row 明细
- Sequence Reset 结果
- Migration Start Time、End Time 和 Duration

发现不一致时，Migration 必须失败并保留 Report，不得静默跳过数据。

## 迁移工具现状

`aries-migrator`（`backend/migrator/`）已实现完整 ETL 管线，CLI 为 clap 子命令（详见 `docs/migration-runbook.md` 的命令示例）：

- `preflight`：只读检查，实现「必须执行的 Preflight」全项，输出 hard errors / violations / warnings 三级结果与源表行数基线；hard error 非零退出并阻止 `migrate`。
- `migrate`：Extract（时间列以字符串提取，按 `--source-offset` 转 UTC）→ Transform（纯函数，逐表单元测试覆盖）→ Load（按 FK 依赖序分批事务写入，`INSERT ... ON CONFLICT (id) DO NOTHING` 幂等，中断重跑即 Resume）→ 结束后对所有保留原 ID 的 IDENTITY 列 `setval` 重置 Sequence。渲染统一复用 `aries-infra` 的 `ComrakMarkdownRenderer`，与线上 Sanitization 一致。支持 `--only`、`--batch-size`、`--truncate-violations`、`--skip-media-download`、`--media-dir`、`--media-base-url`、`--owner-ids`。
- `validate`：行数对比、主键 min/max（剔除整行归档行）、内容 Hash 抽查（源侧同 Renderer 现算）、关联计数、Archive 对账（源行数 = migrated + skipped + archived_rows + failed）、Sequence 核查；任一不一致非零退出并保留 Report。

每次运行生成唯一 Run ID（UUID v7）、机器可读 JSON Report（`--report`）与 Archive JSONL（`--archive`）。已于 2026-09-07 对本机真实旧库完成一次全量演练（migrate + validate + 重跑幂等全部通过）；正式三轮 Rehearsal 与 Cutover 未执行。
